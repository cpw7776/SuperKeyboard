# Migration: AI Dev Workflow Kit v5.5 → v5.6

> **When to use this:** Your project is on v5.5 (`docs/KIT_VERSION` reads `5.5`) and you want to land on v5.6. v5.6 is the "upgrade-system robustness" release driven by the Fossify-Android v5→v5.5 upgrade retro: it adds two new outcome classifications (`surface-absent` and `structurally-divergent`), recognizes `model: inherit` as a valid override, fixes a Pre-Test gate-count drift, renames `docs/CHANGELOG.md` → `docs/KIT_CHANGELOG.md` to disambiguate from the project's feature log, and introduces `docs/KIT_DEVIATIONS.md` as the project's persistent record of intentional deviations.
>
> **When NOT to use this:** You're on v5.4 or earlier — run the prior migrations first (the upgrade-kit prompt walks the chain for you). You're starting fresh — `docs/README.md` Quick Setup drops you on v5.6 directly.
>
> **Philosophy:** v5.6 is mostly upgrade-system improvements (changes to `upgrade-kit.md` itself) that don't affect runtime behavior. The two project-side changes are the CHANGELOG rename and the optional new `KIT_DEVIATIONS.md` file. Risk is low; the rename needs care to not clobber a project's idiosyncratic root-level `CHANGELOG.md` (some adopting projects, e.g. Fossify forks, keep an upstream's `CHANGELOG.md` at repo root — leave it alone).
>
> **Model:** Use **`opus`** for the merge reasoning, especially Phase 2.2 (the CHANGELOG rename, which has the "is this the kit log or something else?" judgment call).
>
> **Stop points:** One — after the state audit (Phase 1), before any rename or write.

**Inputs needed:**
- **PROJECT_ROOT:** path to the project you're upgrading
- **NEW_KIT_ROOT:** path to the v5.6 kit (where this prompt lives)

The migration agent never touches anything outside `PROJECT_ROOT`.

---

## Phase 1: State Audit (READ-ONLY)

**Goal:** Confirm the project is on v5.5 and identify what needs renaming/creating.

### 1.1 Confirm v5.5 starting state

```
1. Read PROJECT_ROOT/docs/KIT_VERSION.
   Expected: "5.5"
   - If "5.6" or higher: STOP. Already migrated.
   - If "5.4" or lower: STOP. Run docs/prompts/upgrade-kit.md from the new kit — it chains v5.4→v5.5 first, then re-invokes this prompt.
   - If file missing: STOP. Project is pre-v5.3; run the upgrade-kit prompt to fingerprint and walk the chain.

2. Confirm v5.5 artefacts:
   - PROJECT_ROOT/docs/CHANGELOG.md exists (the kit changelog file, will be renamed in Phase 2.2)
   - PROJECT_ROOT/.claude/agents/code-quality-agent.md frontmatter says "model: opus" OR "model: inherit" (v5.5 default + the v5.6-recognized override)
   If either differs, surface and ask the user before proceeding.
```

### 1.2 Inventory the CHANGELOG situation

The rename in Phase 2.2 has one risky case: an existing root-level `CHANGELOG.md` that is NOT the kit log (e.g. an upstream's changelog preserved during a Fossify-fork-style adoption). Audit:

```
Check both locations:
  a. PROJECT_ROOT/CHANGELOG.md (repo root)
  b. PROJECT_ROOT/docs/CHANGELOG.md (kit-shipped location since v5.3)

Determine for each:
  - Does it look like a KIT changelog? (heading says "Changelog" + entries are versioned vX.Y + every entry has Files touched + Migration classification)
  - Does it look like a PROJECT/UPSTREAM changelog? (heading mentions the project name, entries are dated releases of the app/library, no kit-version references, no Migration field)

Report what you find. If PROJECT_ROOT/CHANGELOG.md (root) is a non-kit upstream changelog, log it as untouched in Phase 4 → Phase 4 will record this in KIT_DEVIATIONS.md so future upgrades don't re-flag it.
```

### 1.3 Check for an existing KIT_DEVIATIONS.md

```
If PROJECT_ROOT/docs/KIT_DEVIATIONS.md exists, read it. Phase 4 will append to it rather than overwrite.
If it doesn't exist, Phase 4 will copy the template from NEW_KIT_ROOT/docs/KIT_DEVIATIONS.md.
```

### Phase 1 Stop Point

Present:
1. **Starting state:** `KIT_VERSION = 5.5`, code-quality-agent frontmatter (`opus` / `inherit` / other), `docs/CHANGELOG.md` confirmed.
2. **Root CHANGELOG status:** does the project have a root-level `CHANGELOG.md`? Is it kit or project/upstream? (Critical for Phase 2.2 — must NOT touch a non-kit root changelog.)
3. **KIT_DEVIATIONS.md status:** present, absent, or empty.

**Ask the user:**

> "Confirmed: project is on v5.5. Proceed with v5.6? I will:
>   1. Apply gate-count fix (one-word swap in `feature-lifecycle.md` + `CLAUDE_SNIPPET.md`).
>   2. Rename `docs/CHANGELOG.md` → `docs/KIT_CHANGELOG.md` (only the kit log — your root `CHANGELOG.md` will not be touched).
>   3. Create or update `docs/KIT_DEVIATIONS.md` to record any deviations I noticed.
>   4. Update `docs/AGENTS.md` and any project `CLAUDE.md` references to point at the new path.
>   5. Bump `docs/KIT_VERSION` to `5.6`."

WAIT for explicit approval.

## Phase 2: Mechanical Updates

### 2.1 Gate-count fix (Pre-Test block)

The kit's convention is `4 items + process sweep` for the Pre-Test gate block. v5.5 had two stale references showing `5 numbered lines` (feature-lifecycle.md) and `6 items` / `11 items` (CLAUDE_SNIPPET.md sub-agents table). v5.6 aligns them.

If the project's copy of `docs/prompts/feature-lifecycle.md` line ~398 reads `block with 5 numbered lines`, replace with the v5.6 wording from `NEW_KIT_ROOT/docs/prompts/feature-lifecycle.md` (same line). Same treatment for the project's `docs/CLAUDE_SNIPPET.md` sub-agents table rows for `code-quality-agent` (both modes).

If the project has hand-edited these paragraphs (rare), surface and ask.

`surface-absent` is acceptable here — if the project simplified either file and doesn't have those exact paragraphs, log and continue.

### 2.2 Rename `docs/CHANGELOG.md` → `docs/KIT_CHANGELOG.md`

**Critical safety check from Phase 1.2:** if the project has a root-level `CHANGELOG.md` that's NOT the kit log, DO NOT touch it. We are renaming the kit-shipped log at `docs/CHANGELOG.md` (the path v5.3 established), not anything at the repo root.

```
cd PROJECT_ROOT
git mv docs/CHANGELOG.md docs/KIT_CHANGELOG.md
```

Then update in-prose references inside the project's own files (only the path string `docs/CHANGELOG.md`, not the abstract word "changelog"):

- `PROJECT_ROOT/docs/AGENTS.md` — if a "Versioning" section references `docs/CHANGELOG.md`, update to `docs/KIT_CHANGELOG.md`.
- `PROJECT_ROOT/docs/README.md` — same.
- `PROJECT_ROOT/CLAUDE.md` — if it has a Versioning / Workflow Prompts / Context Files table mentioning the kit changelog path, update.
- `PROJECT_ROOT/docs/prompts/upgrade-kit.md` — if a project copy has the old path string, update.
- `PROJECT_ROOT/docs/upgrading/v5.4-to-v5.5.md` — same.

Skip files that don't have the literal path string (most project files reference "the changelog" abstractly — those don't need rewriting). Step 4.5 (CLAUDE.md updates in upgrade-kit.md) handles the CLAUDE.md sync mechanically.

### 2.3 Create or update `docs/KIT_DEVIATIONS.md`

If absent: copy the template from `NEW_KIT_ROOT/docs/KIT_DEVIATIONS.md`. Replace the example bullets with actual deviations from this upgrade's inventory (Phase 1.2 and 1.3 should have flagged: any non-kit root `CHANGELOG.md`, any `model: inherit` overrides, any structurally divergent files the upgrade-kit prompt's Step 2.5 logged).

If present: leave existing entries; append any newly discovered deviations.

If the project has a non-kit root `CHANGELOG.md` (e.g. Fossify-fork upstream changelog), add this entry under "Other project conventions":

> Project keeps a [upstream-name] `CHANGELOG.md` at repo root for upstream tracking — kit-adopt did NOT replace it with the kit's release log; the kit log lives at `docs/KIT_CHANGELOG.md` instead. Upgrade prompts must not touch root `CHANGELOG.md`.

### 2.4 Bump `KIT_VERSION`

```
Edit PROJECT_ROOT/docs/KIT_VERSION
  Replace "5.5" with "5.6"
```

### 2.5 Append the v5.6 KIT_CHANGELOG entry

Read `NEW_KIT_ROOT/docs/KIT_CHANGELOG.md`, locate the `## [v5.6] — YYYY-MM-DD` entry block, and insert it into `PROJECT_ROOT/docs/KIT_CHANGELOG.md` (note: the file was renamed in 2.2, so reference the NEW path) directly above the existing `## [v5.5]` heading. Don't modify other entries.

### Phase 2 commit

```
cd PROJECT_ROOT
git add docs/KIT_CHANGELOG.md \
        docs/KIT_DEVIATIONS.md \
        docs/AGENTS.md \
        docs/README.md \
        docs/prompts/feature-lifecycle.md \
        docs/CLAUDE_SNIPPET.md \
        docs/KIT_VERSION \
        CLAUDE.md  # if it had path-string updates
# Plus the git-rm of the old docs/CHANGELOG.md (handled by git mv)
git commit -m "chore(kit): upgrade to v5.6 (CHANGELOG rename + upgrade-system improvements)"
```

## Phase 3: Verification

### 3.1 Re-fingerprint

```
1. Read PROJECT_ROOT/docs/KIT_VERSION — expect "5.6".
2. Confirm PROJECT_ROOT/docs/KIT_CHANGELOG.md exists; PROJECT_ROOT/docs/CHANGELOG.md does NOT exist.
3. Confirm PROJECT_ROOT/docs/KIT_DEVIATIONS.md exists.
4. Grep PROJECT_ROOT for `docs/CHANGELOG.md` (literal path string) — every hit should be either (a) historical text inside KIT_CHANGELOG.md describing the rename, or (b) referring to a non-kit changelog (root-level, context-level). Surface any other hit as a missed rename.
```

Report each check.

### 3.2 Sanity-check CLAUDE.md references

If `PROJECT_ROOT/CLAUDE.md` references the kit changelog by name in a tables/lists section, confirm it now reads `docs/KIT_CHANGELOG.md`. v5.6 did not change item counts or gate-block formats — any drift surfaced here is pre-existing.

### 3.3 Final commit

If 3.1 or 3.2 found anything that needs a fix, fix it and commit:

```
git commit -m "chore(kit): v5.6 upgrade verification fixes"
```

If everything is clean, no extra commit is needed.
