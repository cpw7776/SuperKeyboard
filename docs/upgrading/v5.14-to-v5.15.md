# Migration: AI Dev Workflow Kit v5.14 → v5.15

> **When to use this:** Your project is on v5.14 (`docs/KIT_VERSION` reads `5.14`) and you want v5.15 — **"operationalize stack-universality at the kit's birth points, make the gate count honestly stack-dependent, and harden the adopt/upgrade flows for non-root and pre-marker installs."** Five connected changes, all additive/guidance (no new phases, sub-agents, or restructuring):
> 1. **`create-testing-agent.md` gains a "Stack Adaptation" section** — the browser vocabulary becomes the *default*, not the assumption. A surface-classification table (`web` / `mobile-native` / `desktop` / `python-data-app` / `cli-library`) tells the generator how to substitute primitives (how you drive it, what "one step" is, how you observe, pass-evidence, `dev_server`/`credentials_source` equivalents, parallel-isolation axis). The browser-shaped body is unchanged — it's now framed as the web default.
> 2. **`feature-lifecycle.md` Phase 5.8 — the gate count is explicitly stack-dependent.** Five gates with a standalone automated test suite; **four** without (Gate #2 folds into the Phase 4.2 build/sideload proof; the suite lesson goes to the Retrospective Gate's Gap A). Propagated as one-line notes to `AGENTS.md`, `CLAUDE_SNIPPET.md`, `README.md`.
> 3. **`README.md` Quick Setup** gains step 0.5 (classify stack + pick kit root) and step 6 (bootstrap a minimal test harness on fresh projects).
> 4. **`upgrade-kit.md`** gains kit-root detection (find `KIT_VERSION`, don't assume repo root — monorepo/subfolder installs) and a "Marker backfill" subsection (leave pre-v5.4/markerless installs marker-safe).
> 5. **BUGFIX:** `.claude/agents/code-quality-agent.md` had one leftover `"NOT one of the four Phase 5.8 final gates"` — the v5.13→v5.14 migration missed it. It becomes `"five"`. **Projects that matched v5.14 vanilla carry this bug and this migration fixes it.**
>
> **Why this change:** real cross-project feedback (8 projects → v5.14 in one batch; see `retrospectives/2026-06-06-cross-project-v5.14/`). 6/8 were not web apps and every one hand-remapped the testing-agent, parallel-testing, and auth slots — because the kit *preached* portability in prose but never operationalized it where a project's testing setup is born. v5.15 fixes that with a lightweight Stack Adaptation layer (not a rigid profile taxonomy — keeping "adapt, don't dictate").
>
> **Universal-drop-in reminder:** this migration *guides*; it does not prescribe one outcome. Every file it touches, reconcile against THIS project's customization state (vanilla → refresh, structurally-divergent → apply surgically/skip, slotted/hand-edited → merge or surface). The changes are **stack-agnostic** — and **most valuable to non-web projects**, which this release finally meets where they are.
>
> **When NOT to use this:** On v5.13 or earlier — run prior migrations first. Starting fresh — README Quick Setup drops you on v5.15.
>
> **Model:** `sonnet`, unless a hand-edited `feature-lifecycle.md` Phase 5.8 or a structurally-divergent `create-testing-agent.md` needs surgical judgment (then `opus`).
>
> **Stop points:** Two — after the state audit (Phase 1), and before the final commit (Phase 5).

**Inputs:** **PROJECT_ROOT** (the kit root inside the target — see `upgrade-kit.md` Inputs §3; may be a package subfolder) and **NEW_KIT_ROOT** (the v5.15 kit). Never touch anything outside PROJECT_ROOT.

## Phase 1: State Audit (READ-ONLY) — STOP after this phase

```
1. Read PROJECT_ROOT/docs/KIT_VERSION. Expected "5.14" (>=5.15 -> done; <=5.13 -> run prior migrations first).
2. Determine the project's TESTING SURFACE (web / mobile-native / desktop / python-data-app / cli-library).
   Cheap signals: build files (build.gradle / *.xcodeproj / Cargo.toml / pyproject.toml / package.json),
   presence of a dev server + browser testing-agent, whether docs/KIT_DEVIATIONS.md already records a
   stack rewrite of testing-agent.md. This classification drives Phases 2 + 3.
3. Classify each file the release touches as vanilla / structurally-divergent / hand-edited:
   - docs/prompts/create-testing-agent.md   (gains Stack Adaptation)
   - docs/prompts/feature-lifecycle.md      (Phase 5.8 gate-count note only — slot-free region)
   - docs/README.md, docs/AGENTS.md, docs/CLAUDE_SNIPPET.md  (one-line gate-count notes)
   - docs/prompts/upgrade-kit.md            (Inputs §3 + Step 2.5 Marker-backfill + v5.15 fingerprint row)
   - .claude/agents/code-quality-agent.md   (the four->five BUGFIX)
4. SUITE CHECK (determine this BEFORE the bug check — it changes what "four" MEANS). Does the project have
   a standalone automated test suite, or is Phase 4 a build/compile/sideload pipeline? Read
   KIT_DEVIATIONS.md FIRST — a machine-readable `Gate count: four (suite-less)` line, or a
   structurally-divergent suite-less testing-agent, is authoritative. Result: the project is FIVE-gate (has
   a suite) or FOUR-gate (suite-less). If suite-less, Phase 2 confirms/sets the sanctioned four-gate
   reduction in KIT_DEVIATIONS.md (and you can retire any ad-hoc local note that "the lifecycle doesn't fit
   our stack").
5. BUG CHECK — **ONLY meaningful for FIVE-gate projects.** grep .claude/agents/code-quality-agent.md for
   "four Phase 5.8 final gates". In a FIVE-gate project that string is the v5.14 vanilla wording bug ->
   Phase 4 fixes it to "five". **In a FOUR-gate (suite-less) project "four" is CORRECT — it is NOT the bug;
   do NOT change it.** The historical bug and a legitimate four-gate count are TEXTUALLY IDENTICAL — the
   suite-check in step 4 is the ONLY thing that distinguishes them. When suite-less, record BUG CHECK as
   "N/A — four is the correct sanctioned count here, not the v5.14 wording bug."
6. ROOT CHECK: confirm you resolved PROJECT_ROOT by finding docs/KIT_VERSION, not by assuming repo root
   (monorepo/subfolder installs). Report where it resolved.
```

**STOP.** Report: version, testing surface, per-file classification, whether the code-quality-agent bug is present, whether the project is suite-less (four-gate candidate), and the resolved kit root. Wait for the user.

  - **HAND-EDITED** → insert the stack-dependent note after the ordered five-gate list (copy the `> **Gate count is stack-dependent…`** block from NEW_KIT_ROOT verbatim; it sits before the **Enforcement:** paragraph). Do not disturb the project's gate wording otherwise.
