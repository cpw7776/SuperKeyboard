# Migration: AI Dev Workflow Kit v5.7 → v5.8

> **When to use this:** Your project is on v5.7 (`docs/KIT_VERSION` reads `5.7`) and you want to land on v5.8. v5.8 is the "verdict expansion + scenario patterns" release covering:
> 1. **`BLOCKED_NEEDS_FIXTURE` and `REQUIRES_INPUT` verdicts** added to the base testing-agent. PASS/FAIL/SKIP/ABORT → PASS/FAIL/SKIP/ABORT/BLOCKED_NEEDS_FIXTURE/REQUIRES_INPUT.
> 2. **Required Scenario Patterns A + C** in the generator (`create-testing-agent.md`). Pattern A = end-to-end submit assertion (`Render:` + `Submit:` lines); Pattern C = REQUIRES_INPUT for ambiguity (kills the "leak finding parked in Reliability Notes" escape route).
> 3. **Pattern B (DB preconditions)** as opt-in via `docs/patterns/db-precondition.md` — NOT applied to your project unless you explicitly opt in during Phase 5 of this migration.
> 4. **KIT_DEVIATIONS.md** template gains a "Project extensions to kit files" category for opt-in pattern adoptions and project-specific extensions.
>
> The load-bearing principle: ambiguity and missing-fixture state must show up as verdicts, not prose. Parent agents act on the Reporting Format verdict counts; anything that lives only in Reliability Notes is easy to miss.
>
> **When NOT to use this:** You're on v5.6 or earlier — run the prior migrations first (the upgrade-kit prompt walks the chain). You're starting fresh — `docs/README.md` Quick Setup drops you on v5.8 directly.
>
> **Special case — projects already carrying Patterns A/C as extensions.** Some projects (notably CoffeeScribe) added "Required Scenario Patterns A/B/C" to `create-testing-agent.md` as a project extension before v5.8 shipped them upstream. Phase 2.5 of this migration explicitly detects the project-side copy and offers to remove it (since the kit vanilla now covers Patterns A and C). Pattern B stays project-side because it's opt-in here too — but it should be re-anchored against `docs/patterns/db-precondition.md`.
>
> **Philosophy:** v5.8 is additive in the base testing-agent and the generator, structurally additive in KIT_DEVIATIONS.md, and opt-in for Pattern B. Most projects' merges will be clean. The complexity is in the dedup step for projects with existing Patterns A/C extensions.
>
> **Model:** Use **`opus`** for the merge reasoning — Phase 2.5's dedup detection requires reading the project's existing pattern text and deciding whether it's semantically equivalent to v5.8 vanilla or carries genuine project-specific content worth preserving.
>
> **Stop points:** Three — after the state audit (Phase 1), after Phase 2.5 dedup (if applicable), and before the final commit (Phase 5).

**Inputs needed:**
- **PROJECT_ROOT:** path to the project you're upgrading
- **NEW_KIT_ROOT:** path to the v5.8 kit (where this prompt lives)

The migration agent never touches anything outside `PROJECT_ROOT`.
