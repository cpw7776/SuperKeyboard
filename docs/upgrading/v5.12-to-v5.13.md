# Migration: AI Dev Workflow Kit v5.12 → v5.13

> **When to use this:** Your project is on v5.12 (`docs/KIT_VERSION` reads `5.12`) and you want v5.13 — "generalized propagation safety net + behind-vanilla detection." Two tooling additions to `upgrade-kit.md`:
> 1. **Post-migration completeness reconciliation** — after a migration runs, the agent diffs the release's CHANGELOG Files-touched against what the migration actually edited, and repairs any stale propagation file (`AGENTS.md`/`CLAUDE_SNIPPET.md`/`README.md`) — *applied per YOUR project's own state*, not a fixed recipe.
> 2. **Behind-vanilla detection** — surfaces lines where the project trails kit-default content an earlier upgrade missed, as opt-in cleanup.
>
> **What's special about this migration:** it is the first to **run the new reconciliation as a one-time backfill.** Earlier migrations (notably v5.9→v5.10) edited the agents but skipped `AGENTS.md`, so many projects on v5.10–v5.12 carry a stale `AGENTS.md` (its testing-agent cell still reads the pre-v5.8 verdict set). Phase 3 repairs that here.
>
> **Universal-drop-in reminder:** this migration *guides*; it does not prescribe one outcome. Every file it touches, the agent reconciles against THIS project's customization state (vanilla → refresh, structurally-divergent → skip, slotted/hand-edited → merge or surface). The same step lands differently in a Next.js app, a Python pipeline, or a native-Android project — that's intended.
>
> **When NOT to use this:** On v5.11 or earlier — run prior migrations first. Starting fresh — README Quick Setup drops you on v5.13.
>
> **Model:** `sonnet`, unless Phase 3's reconciliation hits a hand-edited propagation file (then `opus`).
>
> **Stop points:** Two — after the state audit (Phase 1), and before the final commit (Phase 4).

**Inputs:** **PROJECT_ROOT** and **NEW_KIT_ROOT** (the v5.13 kit). Never touch anything outside `PROJECT_ROOT`.

---

## Phase 1: State Audit (READ-ONLY) — STOP after this phase

```
1. Read PROJECT_ROOT/docs/KIT_VERSION. Expected "5.12" (≥5.13 → done; ≤5.11 → run prior migrations first).
2. Classify docs/prompts/upgrade-kit.md: vanilla (content-diff vs the v5.12 archive) or hand-edited.
   v5.13 should NOT already be present — grep for "Post-migration completeness reconciliation" and
   "Behind-vanilla detection"; if present, surface and ask.
3. BACKFILL SCAN (the point of this release). For each propagation doc the project has
   (docs/AGENTS.md, docs/CLAUDE_SNIPPET.md, docs/README.md), check whether it is STALE relative to
   new vanilla on content a PRIOR release's Files-touched claims to have changed but the project never got.
   Cheapest tell for the known case: does docs/AGENTS.md's testing-agent row still read
   "PASS/FAIL/SKIP/ABORT" only (pre-v5.8), missing BLOCKED_NEEDS_FIXTURE/REQUIRES_INPUT and the
   v5.10 parallel note? If so it's stale — flag for Phase 3.
   Classify each as vanilla / structurally-divergent / hand-edited so Phase 3 knows how to treat it.
```

**STOP.** Report: version, upgrade-kit vanilla-or-hand-edited, and the propagation-staleness findings (which files, what's stale, their customization class). Wait for the user.

---

## Phase 2: Refresh `upgrade-kit.md` (carries the two new sections)

- **Vanilla** → wholesale-replace with the v5.13 copy.
- **Hand-edited** → apply the two additions surgically (Step 4 "Post-migration completeness reconciliation"; Step 2.5 "Behind-vanilla detection"), preserving the project's edits. Surface unreconcilable overlaps as `conflict`.

Verify: `grep -c "Post-migration completeness reconciliation\|Behind-vanilla detection" upgrade-kit.md` ≥ 2.

---

## Phase 3: One-time propagation backfill (the new reconciliation, applied to the chain)

This is the generalized Step 4 reconciliation, run once across the releases the project already passed:

```
1. Read the CHANGELOG `### Files touched` for v5.8 through v5.12 (in NEW_KIT_ROOT/docs/KIT_CHANGELOG.md).
   Collect every propagation file listed (docs/AGENTS.md, docs/CLAUDE_SNIPPET.md, docs/README.md).
2. For each, reconcile against THIS project's copy (from Phase 1.3 classification):
   - VANILLA here → wholesale-refresh from NEW_KIT_ROOT (it picks up every missed propagation edit at once).
   - STRUCTURALLY DIVERGENT → skip; the project owns it (log surface-absent).
   - SLOTTED / HAND-EDITED → apply the missed kit changes inside slots / on top, or surface conflict.
3. Known target: docs/AGENTS.md testing-agent cell → should end up listing the full verdict set
   (PASS/FAIL/SKIP/ABORT/BLOCKED_NEEDS_FIXTURE/REQUIRES_INPUT) + the v5.10 parallel note.
```

Then (optional, opt-in): run **behind-vanilla detection** — diff each non-divergent kit file vs new vanilla; present any out-of-scope stale lines (e.g. a lingering "`CHANGELOG.md` at the kit root" reference) as an opt-in cleanup list. Apply only what the user approves.

---

## Phase 4: Stamp + Commit — STOP before committing

```
1. Write "5.13" to PROJECT_ROOT/docs/KIT_VERSION.
2. Sanity: upgrade-kit.md has both new sections; any stale AGENTS.md now current; KIT_VERSION 5.13.
```

**STOP.** Show the user the refreshed tooling + the propagation repairs (especially the AGENTS.md diff). On approval:

```
chore(kit): upgrade to v5.13 — generalized propagation safety net + behind-vanilla

- Refresh upgrade-kit.md (post-migration completeness reconciliation; behind-vanilla detection)
- One-time backfill: repair propagation files (AGENTS.md, ...) left stale by earlier migrations
- Bump KIT_VERSION 5.12 -> 5.13
```

---

## What this migration does NOT do

- It changes no runtime behaviour, no lifecycle phase, no gate — upgrade tooling only, plus repairing already-stale propagation docs.
- It does not auto-apply behind-vanilla cleanups — those are opt-in, because some divergences are deliberate.
- It does not prescribe how any file lands — the in-project agent reconciles each against this project's own customization state.
