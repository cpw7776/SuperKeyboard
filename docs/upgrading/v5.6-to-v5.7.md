# Migration: AI Dev Workflow Kit v5.6 → v5.7

> **When to use this:** Your project is on v5.6 (`docs/KIT_VERSION` reads `5.6`) and you want to land on v5.7. v5.7 is the "sub-agent reliability" release covering FOUR bundled changes:
> 1. **Phase 2 returns to the orchestrator** — no more sub-agent dispatch for planning.
> 2. **Sub-Agent Supervision Protocol** — structured returns, verify-before-trust via `git show`, bounded scope, for every remaining dispatch.
> 3. **`testing-agent` v2 → v3 self-pacing** — per-action expected-duration estimates, adaptive-cadence watch loop, `ABORT` as a fourth verdict alongside PASS/FAIL/SKIP, `progress.log` for live `tail -f`. Driven by observed 12-hour stalled testing-agent runs.
> 4. **Copy-pasteable next-chat handoffs** — Phase 5.10 now requires a literal paste-ready prompt, not a meta-plan.
>
> The load-bearing principle across all four: verify the artifact (git diff, browser progress, paste-ready prompt), don't trust the summary.
>
> **When NOT to use this:** You're on v5.5 or earlier — run the prior migrations first (the upgrade-kit prompt walks the chain for you). You're starting fresh — `docs/README.md` Quick Setup drops you on v5.7 directly.
>
> **Philosophy:** v5.7 is a STRUCTURAL change to `feature-lifecycle.md` AND `testing-agent.md` AND `create-testing-agent.md` AND existing per-feature test plans. This is NOT a mechanical Find/Replace — projects may have hand-edited or slot-customized the affected regions and those need surgical merging. The bundle is shipped as one release because no project has adopted v5.7 yet — splitting the four changes into separate releases would force adopting projects through an unnecessary migration ladder.
>
> **Model:** Use **`opus`** for the merge reasoning — every phase of this migration involves judgment calls about whether the project has hand-edits in the regions being modified.
>
> **Stop points:** Two — after the state audit (Phase 1) and before the final commit (Phase 5).

**Inputs needed:**
- **PROJECT_ROOT:** path to the project you're upgrading
- **NEW_KIT_ROOT:** path to the v5.7 kit (where this prompt lives)

The migration agent never touches anything outside `PROJECT_ROOT`.

### 2.0 Mode-specific behavior

The orchestrator owns Plan Mode, PRD authoring, ADR authoring, Feature Architecture authoring, plan snapshot, and the testing-agent find-or-create. ### 3.5.3 Retrofit existing per-feature test plans

**This is the most user-visible change.** Every test plan in `docs/testing-agents/*-tests.md` was authored against the v2 template (no expected-duration brackets). After v5.7, the testing-agent will use a default 30s hard cap for every action without a bracket — fine for clicks and navigates, **too short for any feature with legitimate long async operations** (backups, AI generation, file uploads, video processing).

**Early exit — no test plans yet.** If `ls PROJECT_ROOT/docs/testing-agents/*-tests.md` returns nothing (or only a `_template.md`-style scaffold with no real plans), there is nothing to retrofit. Report `Phase 3.5.3 skipped — no per-feature test plans exist yet. New plans authored after v5.7 will use the v3 template directly via the updated create-testing-agent.md.` and proceed to Phase 3.6. **Do not** present the (a)/(b)/(c) choice below — it is meaningless when the answer is "no plans."

```
For each test plan in PROJECT_ROOT/docs/testing-agents/*-tests.md:
1. Read the plan.
2. Identify scenarios that wait for legitimate long async operations (>30s expected).
3. For each such scenario, add `Expected duration (whole scenario):` to the header,
   and `[~Xs]` or `[~X-Ymin]` brackets on the relevant wait steps.
4. Add `default_action_timeout: 30s`, `run_hard_cap: 45min`,
   `progress_log: /tmp/test-evidence/{feature-name}/progress.log` to the Test Configuration yaml.
```

If the user prefers to defer the retrofit and accept that long-async scenarios will ABORT on first v3 run, that's a valid choice — the ABORT report will clearly identify which scenarios need brackets, so the retrofit can happen feature-by-feature as those features are next touched.

**Parallelism for large plan sets.** If the project has more than ~8 plans to retrofit, prefer dispatching to N sub-agents over running the retrofit sequentially in the orchestrator. Per the Sub-Agent Supervision Protocol in `feature-lifecycle.md`, a bounded scope of ~4 plans per dispatch fits comfortably inside ~30 tool calls and avoids the silent-stop class that motivated v5.7 in the first place. Observed wall-clock: 16 plans across 4 parallel Opus sub-agents ≈ 12 minutes; the same retrofit done sequentially in the orchestrator ≈ 45+ minutes. Each sub-agent returns a `SUB-AGENT RETURN` block listing the plans it touched and the commit hash(es); the orchestrator runs `git show --stat <hash>` on each before moving on. Do NOT dispatch when ≤ 8 plans — the supervision overhead exceeds the parallelism win for small sets.

**Stop point (only when at least one real test plan exists):** present the list of test plans + the scenarios that need brackets. Ask the user whether to:
- (a) **Retrofit all now** — apply brackets across all plans before completing the migration.
- (b) **Defer retrofit** — accept first-run ABORTs as the signal for which plans need updating. Add a `KIT_DEVIATIONS.md` note that test plans are on the v2 template and may ABORT on long-async scenarios until updated.
- (c) **Selective retrofit** — name specific plans to update now, defer the rest.

WAIT for choice. Proceed accordingly.
