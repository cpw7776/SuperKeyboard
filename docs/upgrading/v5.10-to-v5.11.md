# Migration: AI Dev Workflow Kit v5.10 → v5.11

> **When to use this:** Your project is on v5.10 (`docs/KIT_VERSION` reads `5.10`) and you want to land on v5.11 — the "upgrade-system robustness" release driven by two convergent downstream upgrade retros. It edits the kit's **own upgrade tooling** (`upgrade-kit.md`) and the **Pattern B opt-in doc** (`db-precondition.md`). It does NOT touch the forward lifecycle, the agents' runtime behaviour, or any context file.
>
> **What changes (all in tooling / opt-in docs):**
> 1. `upgrade-kit.md` — fixed self-referential vanilla heuristic (commit-count no longer gates), canonical real-marker grep ("Marker-matching discipline"), post-migration tooling-file safety net, "project ahead of the kit" superset detection + `superset-preserved` outcome, Step 4.5 stale-fact-correction category.
> 2. `db-precondition.md` — no-SQL auto-skip section; Pattern B rule number 23 → 24 (v5.10's parallel rule now owns 23) with next-free-number guidance.
>
> **Philosophy:** these files are almost always **vanilla** in an adopting project (you don't usually hand-edit the upgrade tooling). So the migration is mostly a wholesale-refresh-if-vanilla. The interesting case is a project that hand-tuned either file — then it's a slot-aware/manual merge.
>
> **This release is self-demonstrating:** it's the first migration written under the new rule "a release that touches `upgrade-kit.md` must refresh it in the migration prompt." Phase 2 below is that refresh.
>
> **When NOT to use this:** You're on v5.9 or earlier — run the prior migrations first (the upgrade-kit prompt chains them). Starting fresh — README Quick Setup drops you on v5.11 directly.
>
> **Model:** `sonnet` suffices unless Phase 2/3 detect a hand-edited tooling file (then `opus` for the merge).
>
> **Stop points:** Two — after the state audit (Phase 1), and before the final commit (Phase 4).

**Inputs needed:**
- **PROJECT_ROOT** and **NEW_KIT_ROOT** (the v5.11 kit, where this prompt lives).

The migration agent never touches anything outside `PROJECT_ROOT`.

---

## Phase 1: State Audit (READ-ONLY) — STOP after this phase

```
1. Read PROJECT_ROOT/docs/KIT_VERSION. Expected "5.10".
   - "5.11"+ → STOP, already migrated.
   - "5.9" or lower → STOP, run upgrade-kit.md (chains earlier migrations first).

2. Classify PROJECT_ROOT/docs/prompts/upgrade-kit.md (the tooling file this release rewrites):
   - CONTENT DIFF vs prior vanilla: prefer NEW_KIT_ROOT/archive/v5.10/docs/prompts/upgrade-kit.md;
     if absent, `git -C NEW_KIT_ROOT show <v5.10-ref>:docs/prompts/upgrade-kit.md`. Empty ⇒ content-vanilla.
   - REAL slot markers: run the canonical grep (it ships zero) —
     grep -nE '(<!-- KIT:SLOT-BEGIN|# KIT:SLOT-BEGIN) [a-z][a-z0-9-]* (-->)?' on the project copy.
   - Record vanilla / hand-edited. (Do NOT use commit count — that's the very bug this release fixes.)

3. Classify PROJECT_ROOT/docs/patterns/db-precondition.md:
   - Present? Many projects don't have it (it ships only if Pattern B was relevant). If absent, skip it in Phase 3.
   - If present: vanilla vs hand-edited (same content-diff method). NOTE whether the project ADOPTED Pattern B
     (look for a Rule 23/24 in testing-agent.md referencing DB preconditions, and a KIT_DEVIATIONS entry).
     If adopted: this is a "project ahead" case — Phase 3 preserves the adoption and only refreshes the doc.

4. Confirm v5.11 NOT already applied: upgrade-kit.md should NOT yet contain "Marker-matching discipline"
   or "superset-preserved". If present, surface and ask.
```

**STOP.** Report: version confirmed, `upgrade-kit.md` vanilla-or-hand-edited, `db-precondition.md` present/absent + Pattern-B-adopted?. Wait for the user.

---

## Phase 2: Refresh `upgrade-kit.md` (the tooling-file rule, applied to itself)

- **If vanilla** (Phase 1.2): wholesale-replace `PROJECT_ROOT/docs/prompts/upgrade-kit.md` with `NEW_KIT_ROOT/docs/prompts/upgrade-kit.md`. Verify byte-identical. Log `applied (wholesale-replace, vanilla)`.
- **If hand-edited**: do NOT clobber. Apply the v5.11 changes surgically (the five `### Changed` bullets in the changelog entry — vanilla heuristic, marker discipline, safety net, superset detection, stale-fact category), preserving the project's hand-edits. Surface anything unreconcilable as `conflict` and STOP.

**Verify:** `grep -c "Marker-matching discipline" upgrade-kit.md` ≥ 1 and `grep -c "superset-preserved" upgrade-kit.md` ≥ 1.

---

## Phase 3: Refresh `db-precondition.md` (only if present)

- **Absent** → skip (project never adopted Pattern B; nothing to refresh).
- **Present and vanilla** → wholesale-replace with the v5.11 copy.
- **Present and the project ADOPTED Pattern B** (Phase 1.3) → this is a superset/project-ahead case:
  - Refresh the *reference doc* `db-precondition.md` to v5.11 (it's documentation).
  - Do NOT touch the project's live Pattern B rule in `testing-agent.md`.
  - **Resolve the rule-number collision if it exists:** if the project carries Pattern B as `Rule 23` AND the project is on v5.10+ (so the parallel-isolation rule also wants 23), confirm the v5.9→v5.10 migration already renumbered one to 24. If not (the collision slipped through), fix it now: keep both rules, renumber Pattern B to the next free number, update the `KIT_DEVIATIONS.md` reference. Record `superset-preserved`.

---

## Phase 4: Stamp + Commit — STOP before committing

```
1. Write "5.11" to PROJECT_ROOT/docs/KIT_VERSION.
2. Sanity check: upgrade-kit.md has the marker-discipline + superset content; db-precondition.md (if present)
   refreshed; any Pattern B adoption preserved with no rule-number collision; KIT_VERSION reads 5.11.
3. If anything was preserved as a superset / renumbered, ensure docs/KIT_DEVIATIONS.md reflects it.
```

**STOP.** Show the user the refreshed tooling file (and any preserved adoption). On approval, commit:

```
chore(kit): upgrade to v5.11 — upgrade-system robustness

- Refresh upgrade-kit.md (vanilla heuristic fix, marker-matching discipline,
  tooling-file safety net, superset detection, stale-fact category)
- Refresh db-precondition.md (no-SQL auto-skip; Pattern B rule 23->24) [if present]
- Preserve any project Pattern B adoption; resolve rule-number collision [if applicable]
- Bump KIT_VERSION 5.10 -> 5.11
```

---

## What this migration deliberately does NOT do

- **It changes no runtime behaviour.** The agents, the lifecycle phases, the gates, and the context docs are untouched. This is upgrade *tooling* + the Pattern B *reference doc*.
- **It does not force Pattern B on anyone.** No-SQL projects stay skipped (now automatically).
- **The payoff is on your NEXT upgrade and any re-run** — the fixed heuristics and the tooling-refresh rule make subsequent upgrades cleaner, especially for projects that are ahead of the kit.
