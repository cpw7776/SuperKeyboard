# Migration: AI Dev Workflow Kit v5.4 → v5.5

> **When to use this:** Your project is on v5.4 (`docs/KIT_VERSION` reads `5.4`) and you want to land on v5.5. The change is small but touches model-rationale prose in several files — adopting projects often customize that prose in their CLAUDE.md, so this prompt walks an agent through a guided reconcile rather than blind find/replace.

> **When NOT to use this:** You're on v5.3 or earlier — run the prior migrations first (the upgrade-kit prompt walks the chain for you). You're starting fresh — `docs/README.md` Quick Setup drops you on v5.5 directly.

> **Philosophy:** v5.5 is a single conceptual shift — the model-split principle moves from "Opus plans, Sonnet executes" to "Opus owns the critical path; Sonnet owns structured execution." The mechanical surface is one frontmatter flip and a handful of paragraph rewrites. The risk is paragraph drift in CLAUDE.md or in adopting-project customizations that quoted the old principle.

> **Model:** Use **`opus`** for the merge reasoning. Don't run this on Sonnet — paragraph reconciliation across CLAUDE.md and customization-rich files needs judgment.

> **Stop points:** Two — after the State Audit (Phase 1), and after the surgical merges (Phase 3), before the final commit lands.

**Inputs needed:**
- **PROJECT_ROOT:** path to the project you're upgrading
- **NEW_KIT_ROOT:** path to the v5.5 kit (where this prompt lives)

The migration agent never touches anything outside `PROJECT_ROOT`.

---

## Phase 1: State Audit (READ-ONLY)

**Goal:** Confirm the project is on v5.4 and inventory anything that needs a guided reconcile.

### 1.1 Confirm v5.4 starting state

```
1. Read PROJECT_ROOT/docs/KIT_VERSION.
   Expected: "5.4"
   - If "5.5" or higher: STOP. Already migrated.
   - If "5.3" or lower: STOP. Run docs/prompts/upgrade-kit.md from the new kit — it chains v5.3→v5.4 first, then re-invokes this prompt.
   - If file missing: STOP. Project is pre-v5.3; run the upgrade-kit prompt to fingerprint and walk the chain.

2. Confirm v5.4 artefacts:
   - PROJECT_ROOT/.claude/agents/code-quality-agent.md contains "KIT:SLOT-BEGIN" (v5.4 slot marker convention)
   - PROJECT_ROOT/.claude/agents/code-quality-agent.md frontmatter says "model: sonnet" (the v5.4 default — this is what we'll flip)
   If either differs, surface and ask the user before proceeding.
```

### 1.2 Inventory the prose that quotes the v5.4 principle

The v5.4 principle ("Opus plans, Sonnet executes") may be quoted verbatim in places the kit doesn't ship by default — most commonly the project's `CLAUDE.md`. Find every quote so we can reconcile each one:

```
Grep PROJECT_ROOT for these strings (case-insensitive), excluding .git/ and archive/:
  - "Opus plans, Sonnet executes"
  - "Opus plans + dispatches + reasons"
  - "Opus plans + dispatches, Sonnet executes"
  - "executes the approved plan via TDD"   (the old Phase 3 row)
  - "executes against a known bug + reproduction + scope"   (the old Phase 4 fix row)

For each hit, capture: file path, line number, surrounding 3 lines.
```

Report the inventory. Don't change anything yet.

### 1.3 Check for project-side overrides

```
Read PROJECT_ROOT/.claude/agents/code-quality-agent.md.
  Inspect the frontmatter `model:` field. Three valid states:
    - `sonnet` → the v5.4 default. v5.5 will flip it to `opus`.
    - `opus` (or a specific Opus snapshot ID) → the project already adopted the v5.5 default ahead of time. Preserve as-is.
    - `inherit` → the project intentionally lets the orchestrator's model flow through. This is a documented override pattern. Preserve as-is; do NOT flip to opus. Log it for the Phase 5 retrospective so the override stays visible.
    - Anything else (e.g. a custom snapshot ID, or a value like `haiku`) → capture the override. Preserve it; surface to the user at the Phase 1 stop point with the v5.5 default for comparison.

Read PROJECT_ROOT/CLAUDE.md (or AGENTS.md if that's where the project keeps agent guidance).
  Note any model-split table or paragraph the project has hand-customized vs the kit's CLAUDE_SNIPPET.md baseline.
  If the project has its own model-split paragraph that diverges substantially from CLAUDE_SNIPPET.md, treat it as project-owned — surface a side-by-side at Phase 3 rather than overwriting.
```

### Phase 1 Stop Point

Present:
1. **Starting state:** `KIT_VERSION = 5.4`, code-quality-agent frontmatter, v5.4 marker confirmed.
2. **Inventory:** every file that quotes the v5.4 principle, with line numbers and snippet.
3. **Override status:** is code-quality-agent's model field already overridden? Does CLAUDE.md have a project-owned model-split paragraph?

**Ask the user:**

> "Confirmed: project is on v5.4 with [N] places that quote the old model-split principle. Proceed with the v5.5 reconcile? I'll flip code-quality-agent to `model: opus`, update the kit-shipped prose in feature-lifecycle.md / AGENTS.md / README.md / CLAUDE_SNIPPET.md / bugfix.md / debug.md / upgrade-kit.md, and walk through each project-owned quote one by one for reconcile."

WAIT for explicit approval. If the user wants to keep the old principle in their own CLAUDE.md (e.g. they have a reason to keep Phase 3 on Sonnet), that's allowed — note it as a documented override in Phase 3 below.

## Phase 2: Mechanical Updates (kit-shipped files only)

These are the kit files the project carries verbatim from the v5.4 ship. Apply the v5.5 versions from `NEW_KIT_ROOT`.

> **Rule:** Use `Edit`, not `Write`. Preserve any slot-content the project filled in. If a paragraph has been hand-edited by the project (Phase 1.3 found it), pause and surface at Phase 3 instead of overwriting here.

### 2.1 Flip `code-quality-agent.md` frontmatter

```
Edit PROJECT_ROOT/.claude/agents/code-quality-agent.md

  old_string:
    model: sonnet
  new_string:
    model: opus
```

UNLESS the project already overrides the model field (Phase 1.3) — `opus`, `inherit`, or any custom value. In that case, leave it as-is. `inherit` in particular is a deliberate project choice (let the orchestrator's model flow through); flipping it would silently break that pattern. Note the override in the Phase 5 retrospective.

### 2.2 Rewrite the code-quality-agent Model paragraph

The "Model:" paragraph (typically line 12 or 18 in v5.4) needs the new rationale. Replace with the v5.5 text:

```
Edit PROJECT_ROOT/.claude/agents/code-quality-agent.md

  old_string:
    > **Model:** `sonnet` (top Sonnet — currently Sonnet 4.6). This agent invokes diagnostic skills (`/code-review`, `/vulnerability-scanner`, `/performance`, `/coding-standards`, etc.) and aggregates output into a structured gate block — the underlying skill quality drives results more than the model. Sonnet is sufficient and ~5× cheaper than Opus.
  new_string:
    > **Model:** `opus` (top Opus — currently Opus 4.7). This agent's gate blocks are decision-grade outputs: a false negative on `/vulnerability-scanner`, `/code-review high`, `/performance`, or `/coding-standards` either ships a real defect (Post-Test mode) or wastes the manual-testing pass that's about to happen (Pre-Test mode). The underlying skills do most of the analysis, but judging which findings warrant the fix loop versus which are noise is itself a reasoning task — worth Opus. (Was Sonnet through v5.4; promoted to Opus in v5.5 alongside Phase 3 — see `feature-lifecycle.md` model split table for the broader principle.)
```

If the project has hand-edited this paragraph (rare — most projects leave the kit's rationale prose alone), surface it at Phase 3 instead of forcing the edit.

### 2.3 Update kit-shipped prose in the seven other files

For each of these files, port the v5.5 text from `NEW_KIT_ROOT/<path>` to `PROJECT_ROOT/<path>` **only for the kit-owned paragraphs** (model split table; Phase 3 dispatch; Phase 4 fix dispatch; appendix diagram; "Model split at a glance" footer; "Mixing model contexts" bullet; Model Setting paragraphs; preamble Model notes; fingerprint table v5.5 row):

- `docs/prompts/feature-lifecycle.md` — model split table (around line 7–21); Phase 3 dispatch (around line 313); Phase 4 fix dispatch TL;DR (around line 426); appendix ASCII diagram and "Model split at a glance" footer (around line 744–780)
- `docs/AGENTS.md` — lifecycle-at-a-glance Phase 3 line; sub-agents table (both code-quality rows); "Mixing model contexts" bullet under common mistakes
- `docs/README.md` — "Model setting" paragraphs
- `docs/CLAUDE_SNIPPET.md` — "Model Split" section; Phase 4 fix sub-agent note
- `docs/prompts/bugfix.md` — Model preamble blockquote
- `docs/prompts/debug.md` — Model preamble blockquote
- `docs/prompts/upgrade-kit.md` — fingerprint table (add the v5.5 row)

Strategy: read each v5.5 file from `NEW_KIT_ROOT`, identify the target paragraph(s), and apply targeted `Edit`s in `PROJECT_ROOT`. **Never `Write` over a whole file** — slot content and project-side hand-edits would be clobbered.

For each edit applied, log: `Applied v5.5: <file>:<paragraph-name>`.

**Surface-absent handling.** Some projects simplify or omit the kit's model-related surface entirely (the retro from one Android-project upgrade observed that 5 of these 7 files had no model-related paragraph to update — the project had collapsed the kit's model-split table into a single one-liner at the top of `feature-lifecycle.md`, and `bugfix.md`/`debug.md` predated v5.2's preamble blockquote convention). For each edit:

- If the target paragraph exists, apply the v5.5 text.
- If the target paragraph does NOT exist (no anchor to land on), log `surface-absent v5.5: <file>:<paragraph-name>` and continue to the next edit. Do not invent surface where none exists. The release applies to the surface the project has; absent surface is a no-op, not a failure.
- If the project pre-declares the absence in `docs/KIT_DEVIATIONS.md`, treat it as already-acknowledged — log briefly and continue without surfacing.

### 2.4 Bump `KIT_VERSION`

```
Edit PROJECT_ROOT/docs/KIT_VERSION
  Replace "5.4" with "5.5"
```

### 2.5 Append the v5.5 CHANGELOG entry

Read `NEW_KIT_ROOT/docs/KIT_CHANGELOG.md` (the file was renamed from `docs/CHANGELOG.md` in v5.6 — if the new kit is v5.5 exactly, use the old name; v5.6+ uses the new name). Locate the `## [v5.5] — YYYY-MM-DD` entry block, and insert it into `PROJECT_ROOT/docs/CHANGELOG.md` directly above the existing `## [v5.4]` heading. Don't modify other entries.

The PROJECT side still has `docs/CHANGELOG.md` at this stage — the rename to `docs/KIT_CHANGELOG.md` happens in the v5.5 → v5.6 migration, not this one. Don't pre-emptively rename.

### Phase 2 commit

```
cd PROJECT_ROOT
git add .claude/agents/code-quality-agent.md \
        docs/prompts/feature-lifecycle.md \
        docs/AGENTS.md \
        docs/README.md \
        docs/CLAUDE_SNIPPET.md \
        docs/prompts/bugfix.md \
        docs/prompts/debug.md \
        docs/prompts/upgrade-kit.md \
        docs/KIT_VERSION \
        docs/CHANGELOG.md
git commit -m "chore(kit): upgrade to v5.5 (mechanical kit-shipped updates)"
```

## Phase 3: Project-Owned Reconcile (JUDGMENT)

**Goal:** for each Phase 1.2 hit that wasn't a kit-shipped file (typically `CLAUDE.md`, project AGENTS docs, or project-side ADRs that reference the model split), present the old vs new principle and decide what to do.

For each hit:

1. Show the user the current text in `PROJECT_ROOT/<file>:<line>`.
2. Show the v5.5 principle from `NEW_KIT_ROOT/docs/CLAUDE_SNIPPET.md` Model Split section.
3. **Ask** (use the kit's standard multiple-choice pattern):
   - **Adopt v5.5 wording verbatim** — replace the project's paragraph with the kit's new text.
   - **Adopt v5.5 principle, keep project-specific phrasing** — agent rewrites the project's paragraph to reflect the new split while preserving voice and project-specific examples.
   - **Keep v5.4 wording (document as override)** — leave the project's text unchanged; add a one-line note in the same file or in `PROJECT_ROOT/CLAUDE.md` explaining why the project is keeping the old principle (e.g. project-specific reason to run Phase 3 on Sonnet).
   - **Skip / not applicable** — the quote is in a historical doc or commit message; leave it.

Apply the user's choice. Log each decision.

### Special case: code-quality-agent model override

If Phase 1.3 found that the project has overridden code-quality-agent's `model:` field to something other than `sonnet`, surface explicitly:

> "Your code-quality-agent is currently set to `<override>`. The v5.5 default is `opus`. Options:
>   1. Adopt v5.5 default (`opus`).
>   2. Keep your override (`<override>`) — I'll add a comment noting it's an intentional override.
>   3. Choose a different value."

### Phase 3 Stop Point

Before committing Phase 3 edits, present a single summary:
- N kit-shipped files updated mechanically in Phase 2.
- M project-owned paragraphs reconciled in Phase 3, with the chosen action per paragraph.
- P overrides documented (if any).

**Ask:** "Proceed with the Phase 3 commit?"

If approved:

```
cd PROJECT_ROOT
git add -A   # only the files Phase 3 touched
git commit -m "docs(kit): reconcile project prose with v5.5 model-split principle"
```

## Phase 4: Verification

### 4.1 Re-fingerprint

```
1. Read PROJECT_ROOT/docs/KIT_VERSION — expect "5.5".
2. Read PROJECT_ROOT/.claude/agents/code-quality-agent.md frontmatter — expect `model: opus` (unless documented override from Phase 3).
3. Grep PROJECT_ROOT/docs/prompts/feature-lifecycle.md for "Phase 3 sub-agent" — expect the row to read "**`opus`**" not "**`sonnet`**".
```

Report each check.

### 4.2 Sanity-check `CLAUDE.md` references

If `PROJECT_ROOT/CLAUDE.md` references specific gate item counts (e.g. "10 items"), line numbers, or model names, grep and confirm none drifted. v5.5 did NOT change item counts, gate-block formats, or sub-agent names — so any drift surfaced here is pre-existing and worth flagging.

### 4.3 Final commit

If Phase 4.1 or 4.2 found anything that needs a fix, fix it and commit:

```
git commit -m "chore(kit): v5.5 upgrade verification fixes"
```

If everything is clean, no extra commit is needed.

## Retrospective (optional but encouraged)

Once the upgrade is complete, you MAY send the kit maintainer the **defect-gated upgrade retrospective** defined in `upgrade-kit.md` Step 6.5 (customizations preserved · drift caught · CLAUDE.md edits · findings). It is defect-gated, **not** a recommendation slot: a clean upgrade reports `Findings: CLEAN — no kit changes indicated` and stops there — do not manufacture recommendations to fill a section. Only genuine defects (wrong result / forced deviation / inconsistency) inform a future release.

For v5.5 specifically, the maintainer wants to hear:
- How many places in your project quoted the old model-split principle.
- Whether the new Opus-heavy critical path materially changed cost or latency for your typical feature.
- Whether you used the documented `sonnet` override for Phase 3 on any feature, and why.
