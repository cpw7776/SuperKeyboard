# Android APK — Build & Sideload (Universal)

> **Purpose.** A drop-in reference for any Android project that ships a debug-signed APK to the developer's own phone via sideload — no Play Store, no TestFlight equivalent, no signed release pipeline. Covers both **native Android** (Kotlin / Java direct, AGP `build.gradle.kts`) and **Capacitor** (web-wrapped React/Vite, AGP Groovy `build.gradle`) projects, since the build & sideload mechanics are 90% the same.
>
> **Audience.** Either a human running these commands, or an AI coding agent running them on the user's behalf. The doc is intentionally explicit about *why* each step matters so an agent doesn't skip the load-bearing parts.
>
> **Proven on:** macOS Apple Silicon, AGP 8.2 (native, Java 17) and AGP 8.5+ (Capacitor 7/8, Java 21). Adapt freely for Linux, Intel Mac, or other framework variants — the pattern holds.

---

## TL;DR — what you're shipping and why

The end product is **one file**: `apk-releases/<AppName>-v<version>-<descriptor>.apk`. The user gets it onto their phone (Syncthing recommended), taps it, and the app installs (or **updates in place**, preserving all data) without ever touching the Play Store.

To make that work reliably across many builds, **three things must be true**:

1. **The APK is signed.** Android refuses to install unsigned APKs. We use a *debug* signing key — same security level as any local dev build — but with a **persistent, checked-in keystore** so the signature is identical across builds and machines.
2. **The signature SHA-256 matches every previous release.** The phone identifies an "update" by `applicationId` + signing certificate. Same cert → in-place update. Different cert → "App not installed (signature mismatch)" and the user has to uninstall (losing all on-device data).
3. **The `versionCode` increases monotonically.** Android refuses to "update" an APK whose `versionCode` is ≤ the installed one.

Everything else is plumbing.

> **Terminology.** People sometimes call sideload APKs "unsigned" — they're not. There is no such thing as an installable unsigned Android APK. The correct term is **debug-signed** (or "self-signed with a debug key"). What makes a build "production" rather than "debug" is using a *separate* release keystore + Play Store signing, which is out of scope for this guide.

---

## What the user experiences (the goal)

1. Agent or developer runs the project's build command (`./gradlew clean assembleDebug --no-daemon`, plus `npm run build && npx cap sync android` first if Capacitor).
2. A descriptively named APK lands in `apk-releases/` (e.g. `MyApp-v1.4.0-photo-capture.apk`).
3. Syncthing pushes the APK to the phone within seconds.
4. User taps the APK on the phone, taps **Install** (or **Update**), and the app updates in place. No data loss. No Play Store. No re-login.

If step 4 ever shows **"App not installed"** with a signature mismatch error, something broke in the keystore pipeline — see Troubleshooting below.

## Project types this guide covers

This guide treats both shapes the same way wherever possible. Steps that differ are clearly tagged.

### Type A — Native Android
- Kotlin or Java directly, no web layer.
- Build files use **Kotlin DSL** (`app/build.gradle.kts`, `settings.gradle.kts`).
- Typical Gradle stack: AGP 8.2, Kotlin 1.9.
- **Java 17** required (see Java version note below).
- Project structure has `app/` at the repo root.

### Type B — Capacitor (web-wrapped)
- React/Vue/Svelte + Vite/Webpack, wrapped via Capacitor for a native shell.
- Build files use **Groovy DSL** (`android/app/build.gradle`).
- Typical Gradle stack: AGP 8.5+, Capacitor 7/8.
- **Java 21** typical and recommended.
- Project structure: web project at repo root, `android/` subfolder generated by `npx cap add android`.
- Adds two pre-build steps: `npm run build` (Vite/Webpack → `dist/`) → `npx cap sync android` (copies `dist/` into the Android assets bundle).

> **React Native / Flutter / KMP?** Out of scope here, but the keystore + sideload + Syncthing pattern transfers cleanly. Adapt the build commands; everything from §3 (keystore) onward is identical.

## 1. Host setup (one-time per machine)

### 1.1 Java version — pick the right one

Choose Java **once per machine** based on the project type you'll mostly build:

| Project type | AGP | Java | Why |
|---|---|---|---|
| Type A — Native, AGP 8.2 | 8.2 | **17** | AGP 8.2 fails the system-modules transform on JDK 21 (`jlink` rejects the SDK 34 `core-for-system-modules.jar`). Stay on 17 until you bump AGP to 8.5+. |
| Type A — Native, AGP 8.5+ | 8.5+ | 21 | Once on AGP 8.5+, JDK 21 is fine. |
| Type B — Capacitor 7/8 | 8.5+ | **21** | Capacitor's Gradle expects modern toolchain. Java 17 will fail with confusing class-version errors. |

If you maintain projects of both types on one machine, you'll need both JDKs installed and switch `JAVA_HOME` per-session. `direnv` or a per-project `.env`-style helper makes this painless.

### 1.2 macOS (Apple Silicon — primary supported host)

```bash
brew install openjdk@17    # for Type A (or AGP 8.2 anywhere)
brew install openjdk@21    # for Type B (or AGP 8.5+ anywhere)
brew install --cask android-commandlinetools
```

Resulting paths:
- Java 17 → `/opt/homebrew/opt/openjdk@17`
- Java 21 → `/opt/homebrew/opt/openjdk@21`
- Android SDK root → `/opt/homebrew/share/android-commandlinetools`

### 1.3 macOS (Intel)

Same Homebrew commands; Homebrew's prefix is `/usr/local`:
- Java 17 → `/usr/local/opt/openjdk@17`
- Java 21 → `/usr/local/opt/openjdk@21`
- Android SDK root → `/usr/local/share/android-commandlinetools`

### 1.4 Linux (Debian/Ubuntu)

```bash
sudo apt install openjdk-17-jdk    # or openjdk-21-jdk
# Android cmdline-tools: download zip from developer.android.com,
# unzip into ~/Android/Sdk/cmdline-tools/latest/
export ANDROID_HOME="$HOME/Android/Sdk"
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64    # or -21-
```

### 1.5 Accept SDK licenses + install required components (run once)

Adapt the env paths to your host:

```bash
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools
export JAVA_HOME=/opt/homebrew/opt/openjdk@17        # or @21
export PATH=$JAVA_HOME/bin:$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH

yes | sdkmanager --licenses >/dev/null 2>&1
sdkmanager "platform-tools" "build-tools;34.0.0" "platforms;android-34"
```

Verify:

```bash
java -version           # must report the version you intended (17.x or 21.x)
sdkmanager --list_installed | head
```

### 1.6 Per-session env block (every shell that runs Gradle)

Either add to `~/.zshrc` (if you build one project type), or paste at the top of each session (if you switch between types):

```bash
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools
export JAVA_HOME=/opt/homebrew/opt/openjdk@17        # or @21 — match the project
export PATH=$JAVA_HOME/bin:$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH
```

> **Gotcha.** macOS's bundled `java` will fail Gradle / AGP / Kotlin with confusing class-version errors. Always point `JAVA_HOME` at the correct project JDK before building.

## 2. One-time setup per project clone

### 2.1 `local.properties`

Tells Gradle where the Android SDK is. **Machine-specific — git-ignore it, never commit.**

- Type A: write at repo root → `<repo>/local.properties`
- Type B: write inside the Android subproject → `<repo>/android/local.properties`

Contents (adapt to your host):

```properties
sdk.dir=/opt/homebrew/share/android-commandlinetools
```

If the file is missing or wrong, Gradle either errors with `SDK location not found` or silently picks the Android Studio default at `~/Library/Android/sdk`, which usually isn't what you want.

### 2.2 (Type B only) `vite.config.{js,ts}` — `base: './'` is mandatory

```js
export default defineConfig({
  plugins: [react()],
  base: './',          // <-- without this, the WebView shows a blank screen
});
```

Reason: Android's WebView serves the bundle from `file://` (or `https://localhost` via Capacitor scheme). Absolute asset paths (`/assets/index.js`) won't resolve; relative ones (`./assets/index.js`) will. Most common cause of "blank screen / LOADING… forever" on first sideload.

### 2.3 (Type B only) Bootstrap the Android subproject if it doesn't exist

```bash
npm install --save @capacitor/core @capacitor/android
npm install --save-dev @capacitor/cli
npx cap init "<App Name>" com.<owner>.<app>     # writes capacitor.config
npx cap add android                             # creates android/
```

### 2.4 Persistent debug keystore (THE load-bearing part — both types)

> **This is the magic that makes "tap the file and the app updates" work.** Without a persistent keystore, every clean build on a slightly different state of the machine produces a fresh debug key → the phone refuses to install over the previous APK with "App not installed (signature mismatch)".

#### Generate the keystore (run once per project, then commit it)

Pick a stable directory name. Either is fine; `keystore/` is shorter; `mobile-keystore/` avoids confusion with backend signing keystores you might add later. Be consistent within the project.

```bash
mkdir -p keystore
keytool -genkey -v \
  -keystore keystore/<app-name-lower>-debug.keystore \
  -alias <app-name-lower> \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -storepass <app-name-lower>-debug -keypass <app-name-lower>-debug \
  -dname "CN=<AppName> Debug, OU=Personal, O=<AppName>, L=Local, S=Local, C=AU"
```

Example for an app called "FinTrack":

```bash
keytool -genkey -v \
  -keystore keystore/fintrack-debug.keystore \
  -alias fintrack \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -storepass fintrack-debug -keypass fintrack-debug \
  -dname "CN=FinTrack Debug, OU=Personal, O=FinTrack, L=Local, S=Local, C=AU"
```

#### Wire the keystore into the build

##### Type A — Native (Kotlin DSL)

In `app/build.gradle.kts`, inside the `android { ... }` block, **just above `buildTypes`**:

```kotlin
signingConfigs {
    getByName("debug") {
        storeFile = rootProject.file("keystore/<app-name-lower>-debug.keystore")
        storePassword = "<app-name-lower>-debug"
        keyAlias = "<app-name-lower>"
        keyPassword = "<app-name-lower>-debug"
    }
}
```

The default `debug` build type already uses the `debug` signing config — no further wiring needed.

##### Type B — Capacitor (Groovy DSL)

In `android/app/build.gradle`, inside the `android { ... }` block:

```groovy
android {
    // ...

    signingConfigs {
        debug {
            storeFile file("../../keystore/<app-name-lower>-debug.keystore")
            storePassword "<app-name-lower>-debug"
            keyAlias "<app-name-lower>"
            keyPassword "<app-name-lower>-debug"
        }
    }

    buildTypes {
        debug {
            signingConfig signingConfigs.debug
        }
        release {
            // production signing goes here later — out of scope
        }
    }
}
```

> **`../../` matters.** `build.gradle` lives at `android/app/build.gradle`, so the relative path needs two parent hops to reach `<repo>/keystore/`.

#### Capture the canonical fingerprint

Build once, then record the SHA-256 so future builds can verify they're producing the same signature.

> **Important — use `apksigner`, not `keytool -printcert -jarfile`.** AGP 8.0+ ships APKs with v2/v3-only signing schemes. `keytool -printcert -jarfile` only reads v1 / JAR-signed entries in `META-INF` and will silently print nothing useful on v2/v3-only APKs. `apksigner verify --print-certs` reads v2/v3 signature blocks correctly and works across all schemes — universal correct answer.

```bash
$ANDROID_HOME/build-tools/34.0.0/apksigner verify --print-certs \
    app/build/outputs/apk/debug/app-debug.apk \
    | grep -i "SHA-256 digest"
```

(For Type B, the path is `android/app/build/outputs/apk/debug/app-debug.apk`.)

Paste the resulting hex string into your project's `apk-releases/BUILD.md` (or equivalent) as the **canonical fingerprint**. Every subsequent debug build must produce that exact value. If a build ever produces a different SHA-256, **stop and investigate** — somewhere the persistent keystore wiring broke.

#### Commit the keystore

> **Yes — commit `keystore/<app-name-lower>-debug.keystore` to the repo.** The whole point is that everyone (the user, future agents, future machines) shares it. The password is checked into `build.gradle{,.kts}`, so the keystore isn't a secret. This pattern is **only safe for sideload-only debug builds** — never use it for a release keystore intended for the Play Store.

## 3. Per-build flow

### 3.1 Bump the version (both types)

##### Type A — `app/build.gradle.kts`

```kotlin
defaultConfig {
    versionCode = 2          // increment by 1 each release — must always increase
    versionName = "1.1.0"    // human-readable — bump per feature/major/minor
}
```

##### Type B — `android/app/build.gradle`

```groovy
defaultConfig {
    applicationId "com.<owner>.<app>"
    versionCode 17                  // monotonic integer — bump on every build
    versionName "3.17.0"            // semver display string
}
```

> **Both must change.** Android uses `versionCode` (integer) for the "is this newer?" check, but `versionName` (string) is what the user sees on the about screen. Bumping only `versionName` will cause the install to silently no-op as a downgrade.

### 3.2 (If applicable) Export build-time secrets

If the project bakes API keys in via `BuildConfig`:

```bash
export <PROJECT>_API_KEY="..."
```

If unset, most projects fall back to a placeholder string and the API will 401 at runtime — that's the intentional loud-failure mode.

### 3.3 Build

##### Type A — Native

```bash
cd /path/to/project
./gradlew clean assembleDebug --no-daemon
```

Typical wall time on Apple Silicon: 60–120 s cold, ~30 s warm.

##### Type B — Capacitor

```bash
cd /path/to/project
npm install                          # only on first clone or when deps changed
npm run build                        # Vite/Webpack → dist/ (or build/)
npx cap sync android                 # copies dist/ → android/app/src/main/assets/public/
cd android
chmod +x gradlew                     # only first time
./gradlew clean assembleDebug --no-daemon
```

Typical wall time: 30–90 s cold, ~20 s warm.

> **Always use `--no-daemon` on a memory-constrained Mac (16 GB or less).** Daemons hold ~1 GB resident even when idle. On a workstation with 64 GB+ you can drop `--no-daemon` for slightly faster repeat builds.

### 3.4 Verify signature, validate, copy

```bash
# Both types — adjust path to apk based on type
APK=app/build/outputs/apk/debug/app-debug.apk            # Type A (run from repo root)
# APK=android/app/build/outputs/apk/debug/app-debug.apk  # Type B (run from repo root)

# 3.4a — Verify the signature SHA-256 matches the canonical fingerprint
$ANDROID_HOME/build-tools/34.0.0/apksigner verify --print-certs $APK \
    | grep -i "SHA-256 digest"
# Compare against the canonical fingerprint recorded in apk-releases/BUILD.md.
# They must match exactly. If not, STOP and investigate.

# 3.4b — Type B only: confirm web assets actually got bundled
# (Catches "blank screen" *before* delivery to the phone)
python3 -c "
import zipfile
with zipfile.ZipFile('$APK') as z:
    paths = [f for f in z.namelist() if f.startswith('assets/public/')]
    assert paths, 'NO web assets in APK — npm run build / cap sync did not run or failed'
    print(f'OK: {len(paths)} web-asset entries bundled')"

# 3.4c — Copy with a descriptive filename into apk-releases/
# Type A version-name extraction
VERSION=$(grep versionName app/build.gradle.kts | head -1 | grep -oE '"[^"]+"' | tr -d '"')
# Type B version-name extraction
# VERSION=$(grep versionName android/app/build.gradle | head -1 | grep -oE '"[^"]+"' | tr -d '"')

cp $APK apk-releases/<AppName>-v${VERSION}-<descriptor>.apk
```

#### Descriptor convention

Short kebab-case noting *what's actually in this build*. Examples:

- `<AppName>-v1.1.0-voice-transcription.apk` (new feature)
- `<AppName>-v1.1.1-fix-calendar-crash.apk` (bug fix)
- `<AppName>-v1.2.0-E5+E6-photo-and-pdf.apk` (multi-epic)

The descriptor lets you and the user see at a glance what's in each historical APK without opening it.

### 3.5 Kill orphan Gradle processes

Especially important on memory-constrained Macs.

```bash
pkill -f "gradle.*daemon|kotlin-compiler" 2>/dev/null
ps aux | grep -E "gradle.*daemon|kotlin-compiler" | grep -v grep
```

If `ps` returns nothing, you're clean.

## 4. Deliver to the phone — Syncthing (recommended)

A USB cable + `adb install -r` works, but it's friction every cycle. **Syncthing is the right tool for the sideload-test loop** because the phone gets the new APK within seconds of the build finishing, with zero manual transfer step.

### 4.1 One-time Syncthing setup

1. Install Syncthing on Mac (`brew install syncthing`) and on Android from F-Droid (the official Play Store version is no longer maintained — F-Droid has the canonical fork).
2. Pair the two devices (scan QR or paste device IDs).
3. Share a folder both directions:
   - **Mac side:** `<project>/apk-releases/`
   - **Phone side:** any folder reachable from the system file manager (e.g. `Internal storage/MyApp-APKs`).
4. Open Syncthing on the phone, accept the share, pick the destination.
5. **Phone-side battery setting:** disable battery optimization for Syncthing, otherwise Android will idle the daemon and APKs won't appear until you next open the app.

### 4.2 Per-build delivery — automatic

The `cp ... apk-releases/...` step in §3.4c lands the APK in Syncthing's watched folder. Syncthing pushes it to the phone within ~5–15 seconds (faster on the same Wi-Fi, slower over the relay).

Tell the user the filename + what to test, then wait.

### 4.3 Alternatives (if Syncthing isn't an option)

| Method | When it makes sense |
|--------|--------------------|
| AirDrop / Quick Share / Nearby Share | One-off, no recurring loop |
| Google Drive / Dropbox / Nextcloud | Cross-platform team, occasional builds |
| Email attachment to self | Slow + cluttered, but always available |
| `adb install -r app-debug.apk` over USB | Tightest dev loop if the cable is right there |
| `gh release create` + download URL | Distributing to outside testers |

Syncthing wins for a solo developer doing many builds per day — local, private, silent, no cloud.

## 5. On-device install (sideload)

### First time on a given device

1. Open the synced folder on the phone with the system file manager.
2. Tap the `.apk`.
3. If prompted: **Settings → Install unknown apps → [your file manager] → Allow.**
4. Tap **Install**.
5. Open the app from the launcher.

### Subsequent updates (with persistent debug keystore wired correctly)

1. Tap the new `.apk` in the synced folder.
2. Tap **Update**.
3. Same `applicationId` + same signature → **in-place update**, all on-device data preserved. No re-login. No data wipe.

> **First install ever** of a persistent-keystore build may require an uninstall of any prior dev build that was signed with Gradle's auto-generated debug key (different signature). After that one-time uninstall, every subsequent update goes in-place forever.

## 6. `apk-releases/` folder convention

```
apk-releases/
├── BUILD.md                                # project-specific build doc — record the canonical SHA-256 here
├── <AppName>-v1.0.0-initial.apk
├── <AppName>-v1.1.0-voice-transcription.apk
├── <AppName>-v1.1.1-fix-calendar-crash.apk
└── <AppName>-v1.2.0-photo-capture.apk
```

- One APK per shipped feature/fix.
- Filename = version + descriptor (see §3.4c).
- `BUILD.md` records the **canonical SHA-256 fingerprint** plus any project-specific quirks (env vars to export, version-bump rules, etc.).
- Whether to `.gitignore` the `*.apk` files is the user's call:
  - **Commit them** if you want a reviewable history of what was actually shipped (good for personal/solo projects, lets you roll back to a known-good APK fast).
  - **Ignore them** if the repo needs to stay slim — they're re-derivable from a tagged commit.

## 7. What NOT to commit (and what TO commit)

| Path | Commit? | Reason |
|------|---------|--------|
| `node_modules/` | ❌ | Standard JS exclusion |
| `dist/` (Type B) | ❌ | Generated by `npm run build` |
| `app/build/` or `android/app/build/` | ❌ | Gradle build outputs — derivable, churn |
| `.gradle/` or `android/.gradle/` | ❌ | Gradle's per-machine cache |
| `local.properties` (root or `android/`) | ❌ | Hardcoded local SDK path — different per machine |
| **Release keystores** | ❌ | Real secrets — rotate via secure storage |
| **Debug keystore** (`keystore/<app>-debug.keystore`) | ✅ | The whole pattern depends on every machine sharing it |
| `apk-releases/*.apk` | optional | See §6 |

## 8. Troubleshooting catalogue

### `SDK location not found`
`local.properties` is missing or wrong (or in the wrong folder for the project type — root for Type A, `android/` for Type B). Set:
```properties
sdk.dir=/opt/homebrew/share/android-commandlinetools
```

### `Unsupported class file major version 65` (or 61 / 59)
`JAVA_HOME` is pointing at the wrong JDK. Re-export the version that matches the project (see §1.1):
```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@17    # or @21
export PATH=$JAVA_HOME/bin:$PATH
java -version       # must print the right major version
```

### `App not installed` / signature mismatch on phone
Either:
- The build's signature SHA-256 doesn't match the canonical fingerprint. Confirm `signingConfigs.debug` actually points at the persistent keystore, not Gradle's auto-generated one.
- The phone has a previous build signed with a different debug key (e.g. from before you added the persistent keystore, or from a different machine). Uninstall once; future updates install in-place.

### `Could not find Android SDK Build-Tools 34.0.0`
```bash
sdkmanager "build-tools;34.0.0"
```

### Gradle hangs / OOMs the Mac
- You almost certainly forgot `--no-daemon` on a 16 GB Mac.
- Kill: `pkill -f "gradle|kotlin-compiler|java"`
- Re-run with `--no-daemon`.

### API calls return 401 from the installed APK
A required env var (e.g. `<PROJECT>_API_KEY`) was unset at build time → the APK has the placeholder string baked in. Re-export the env var, rebuild, re-deliver.

### `keytool -printcert -jarfile` shows no signature info
You're on AGP 8.0+ which uses v2/v3-only signing. Use `apksigner` instead (universal correct answer):
```bash
$ANDROID_HOME/build-tools/34.0.0/apksigner verify --print-certs <apk>
```

### Phone says "this version is older" when installing
You bumped `versionName` but not `versionCode`. Both must increase. `versionCode` is what Android compares.

### (Type B) Blank screen / "LOADING…" forever on the phone
- Is `vite.config.{js,ts}` set to `base: './'`? **Most common cause.**
- Did `npx cap sync android` run **after** `npm run build`?
- Does `android/app/src/main/assets/public/index.html` exist?
- Are bundle asset references relative (`./assets/...`), not absolute (`/assets/...`)?
- The pre-flight Python check in §3.4b catches this *before* delivery — wire it into your build script.

### (Type B) `Could not resolve project :capacitor-android`
Capacitor plugin sync drifted. Re-run:
```bash
npx cap sync android
```

### (Type B) Gradle dependency resolution flaky
```bash
cd android
./gradlew clean --no-daemon
./gradlew assembleDebug --no-daemon --refresh-dependencies
```

### (Type B) App data disappears between launches
On native Android, `localStorage` doesn't persist reliably across the app process being killed. Use `@capacitor/preferences` for everything that must survive a relaunch.

### APK is suspiciously large (> ~15 MB for a basic app)
- Type A: check for accidentally-bundled large drawables, raw assets, or vendored libs.
- Type B: run `du -sh dist/*` and inspect the bundle. Common culprits: an accidental `import * from 'lodash'`, dev-only deps leaking into prod, source maps shipping.

### Build succeeds, but APK doesn't appear in Syncthing folder on the phone
- Confirm the Mac-side `apk-releases/` folder shows the new file.
- Open Syncthing on Mac → folder is "Up to Date" and "Shared with <phone>"?
- Open Syncthing on phone → same folder is "Up to Date" and not paused?
- Phone has battery optimization off for Syncthing? (Else it idles in the background.)

## 9. Canonical one-liners (TL;DR — copy/paste)

Replace `<AppName>` and `<descriptor>` per build.

### Type A — Native

```bash
cd /path/to/project && \
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools && \
export JAVA_HOME=/opt/homebrew/opt/openjdk@17 && \
export PATH=$JAVA_HOME/bin:$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH && \
./gradlew clean assembleDebug --no-daemon && \
VERSION=$(grep versionName app/build.gradle.kts | head -1 | grep -oE '"[^"]+"' | tr -d '"') && \
cp app/build/outputs/apk/debug/app-debug.apk \
   apk-releases/<AppName>-v${VERSION}-<descriptor>.apk && \
$ANDROID_HOME/build-tools/34.0.0/apksigner verify --print-certs \
    apk-releases/<AppName>-v${VERSION}-<descriptor>.apk | grep -i "SHA-256 digest" && \
pkill -f "gradle.*daemon|kotlin-compiler" 2>/dev/null
```

### Type B — Capacitor

```bash
cd /path/to/project && \
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools && \
export JAVA_HOME=/opt/homebrew/opt/openjdk@21 && \
export PATH=$JAVA_HOME/bin:$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH && \
npm run build && \
npx cap sync android && \
cd android && \
./gradlew clean assembleDebug --no-daemon && \
cd .. && \
VERSION=$(grep versionName android/app/build.gradle | head -1 | grep -oE '"[^"]+"' | tr -d '"') && \
cp android/app/build/outputs/apk/debug/app-debug.apk \
   apk-releases/<AppName>-v${VERSION}-<descriptor>.apk && \
$ANDROID_HOME/build-tools/34.0.0/apksigner verify --print-certs \
    apk-releases/<AppName>-v${VERSION}-<descriptor>.apk | grep -i "SHA-256 digest" && \
pkill -f "gradle.*daemon|kotlin-compiler" 2>/dev/null
```

The final `grep` line should print the project's canonical SHA-256 fingerprint. If it doesn't, **stop and investigate before sending the APK to the user**.

Syncthing handles delivery — within seconds, the phone sees the new APK in its synced folder.

## 10. Adapting this guide to a new project — checklist

Drop this file into the new project as `apk-releases/BUILD.md` (or keep it at the repo root — wherever the agent will look).

### Both types

- [ ] Host setup done (Java 17 or 21 + Android SDK + licenses, see §1).
- [ ] `local.properties` written (root for Type A, `android/` for Type B), git-ignored.
- [ ] Persistent debug keystore generated under `keystore/`, committed (§2.4).
- [ ] Keystore wired into the build (`signingConfigs.debug` — Kotlin DSL for Type A, Groovy for Type B).
- [ ] First build completes; SHA-256 of the signing cert recorded as the **canonical fingerprint** in `apk-releases/BUILD.md`.
- [ ] First on-device install works; subsequent installs **update in place** (verify by installing v2 over v1 without uninstalling).
- [ ] `apk-releases/` folder exists; Syncthing share configured to push to the phone.
- [ ] `versionCode` / `versionName` rules understood (both must bump per build, monotonic integer for `versionCode`).

### Type A — Native specifics

- [ ] `app/build.gradle.kts` has the `signingConfigs.debug` block with `getByName("debug")` Kotlin syntax.
- [ ] Project compiles on Java 17 (or whichever version matches the AGP).
- [ ] Any required env-var secrets are documented in `apk-releases/BUILD.md`.

### Type B — Capacitor specifics

- [ ] `vite.config.{js,ts}` has `base: './'`.
- [ ] `npx cap add android` has been run; `android/` directory exists and builds.
- [ ] `android/app/build.gradle` has the `signingConfigs.debug` block with Groovy syntax + `../../keystore/...` relative path.
- [ ] Project compiles on Java 21.
- [ ] Pre-flight script (or §3.4b inline command) catches "no web assets bundled" before delivery.
- [ ] Persistent storage uses `@capacitor/preferences`, not `localStorage`, for anything that must survive a relaunch.

When all boxes are checked, the project has a clean APK build → sync → sideload → update-in-place loop, and every future release is one canonical command away.
